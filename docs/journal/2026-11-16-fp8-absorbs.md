# Journal: the MLA absorbs from kv_b_proj's FP8 codes (#42), 2026-11-16

This journal records #42: the two matvecs around MLA decode that read `kv_b_proj`. One absorbs each
head's query into the latent space; the other takes the attended latents back out to each head's value.
It also covers the first GPU run of #43 (no indexer at contexts within index_topk).
Evidence folders:
- `evidence/h200-20261116-k`: GPU tests, profiles before the fix, and the README for all three folders
- `evidence/h200-20261116-k5`: profiles and the variant sweep
- `evidence/h200-20261116-k5v`: the full-width check

All timings are from the same NVIDIA H200 VM as before, now with Vx main 4f966fd6 built on the pod.

## Where we started

In the like-for-like profile (#40), the absorbs were float32 `matvec_heads` on a dequantized copy of
`kv_b_proj`: 11.5 + 11.7 us a layer, against SGLang's 5.9 + 6.5. `kv_b_proj` is block FP8 in the checkpoint,
so a quarter of the bytes was available.

## First version: per-head layouts (not used on GLM-5.3)

`fp8_matvec_heads_cvt` was `fp8_matvec_cvt_tiles` with an x offset per group of rows. ResidentGLM laid out
the query absorb's matrix (each head's nope block transposed) and the value absorb's (each head's value
rows) once, keeping every 128 x 128 block's scale. That needs nope, value and rank to be multiples of
128. The CPU test used nope 128, and the commit message said GLM-5.3's widths are 128 / 128 / 512.

They are not: GLM-5.3's nope is 192 and its value 256. The first full-width GPU check gave the same
launches and uploaded bytes as before #42, because ResidentGLM had fallen back to float32. Its step
profile still showed `matvec_heads`.

## Heads of 448 rows

`kv_b_proj` is 64 heads x 448 rows (192 nope + 256 value) by 512 latent columns, with a scale for each
128 x 128 block. 448 = 3.5 blocks, so heads 2k + 1 start 64 rows into a block, and one block of scales
can cover the end of one head and the start of the next.

The fix reads the matrix as stored, each row with its own block's scale:
- **Value absorb.** Output row (h, v) is stored row 448 h + 192 + v. The macro under the kernel
  (`fp8t_pair_tile!`) already took separate offsets and scale bases for its two rows, so the new
  `fp8t_tiles_rows_ab_at!` passes two given rows; the kernel maps output rows to stored ones with
  `period` and `offset`.
- **Query absorb, first try.** Each head's nope block transposed (512 rows of 192), moved right by
  (448 h) mod 128 zero columns and padded to 256, so that each 128 columns map to one stored block. The x
  offset moved back by the same amount; zero codes contribute nothing. The CPU test passed at nope 192 /
  value 256 (it fails if the shift is dropped). On the H200 the value absorb took 7.8 us in the step, but
  the query absorb took 15.9: worse than float32. With 32768 rows of 256 columns, each warp reads two
  words a lane and then reduces two rows.

## The query absorb as column sums

q_latent[h][r] = sum over d < 192 of W[448 h + d][r] q[h][d]. In the stored layout, a lane can own one
word (4 latent columns) and walk down the head's 192 nope rows: the warp's reads are 128 contiguous bytes
a row, there is no reduction across lanes, and the transposed copy goes. `fp8_matvec_cols_cvt` takes one
head's 128 columns a block, splits the rows among the subgroups, and sums the subgroups' partials in
shared memory at the end. Both absorbs now share one upload of the codes and scales. It took 7.7 us in
the step with 8 subgroups and four rows a step.

That is still about 0.8 TB/s: too few loads in flight. A sweep of generated variants, each kernel timed as
a CUDA graph with L2 flushed:
- **Query.** 16 subgroups with all twelve of their rows' loads issued first: 8.4 us, against 10.9 for
  the first version. Fewer subgroups or rows a step, and 24 or 32 subgroups, were slower.
- **Value.** Four rows a warp: 9.3 us, against 10.5 for two. Eight rows were slower.
- **Register budgets.** A `spawn-maxnreg` budget made neither faster (the chosen kernels use 32 and
  56 registers).

## Result

In the decode step (nsys, context 1000; 3000 the same):

| absorb | float32 | FP8 | SGLang |
|---|---|---|---|
| query | 11.4 us | **5.4 us** | 5.9 us |
| value | 11.8 us | **6.3 us** | 6.5 us |

The full-width FP8 check (4 layers, 48 tokens): logits within 9.1e-6 of float32 on the dequantized
weights, the same top token, 13.86 GiB uploaded instead of 14.12.

## #43 on the GPU

Every GPU test passes on the 4f966fd6 toolchain, nothing skipped, including #45's graph tests. At context
1000 the decode step has no `index_scores_at` or top-k kernel. At 2049 and 3001 tokens (past index_topk
2048) it has the same ones as before: `index_scores_at` 11.4 us, `topk_chunks_at` 51.0 us, `topk_merge_at`
5.8 us. Against SGLang's 3.6 and 6.0 us, these are now the largest gaps in the attention block (#32).
